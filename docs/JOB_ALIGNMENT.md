## 可以作为项目证据的内容

- 一次可复现的任务：原始缺陷、源文件版本、基线失败、模型调用、工具轨迹、修改、重新执行结果、最终 diff。
- 明确区分使用真实模型的运行、离线确定性演示、模拟执行器测试，以及 Docker 内实际执行的结果。
- 对失败的诚实记录：超时、模型格式错误、预算耗尽、测试不通过、取消和环境缺失，均不得显示为修复成功。
- 对验证范围的说明：测试通过只说明当前测试覆盖；隐藏测试在 Agent 文件工具中不可读，不代表同一容器内的恶意 Python 无法读取或干扰它们。
- 对执行边界的说明：容器不应接收 API Key、宿主工作目录、Docker socket 或网络访问；生产隔离需求仍需独立评估。
- 对个人贡献的说明：使用了哪些已有工具，自己设计和实现了什么，能够独立调试并解释什么。

## 投递前建议完成的检查

以下是本项目的工程建议，不是字节官方录用门槛。

1. 让另一位开发者按照 README 完成安装、配置、运行和结果复现，记录实际遇到的问题。
2. 使用固定版本的任务、模型配置和容器镜像报告评测结果。公开任务数量、分母、修复率、耗时和 token 用量，避免只展示成功案例。
3. 将提示词调试使用的任务与最终评测任务分开。在查看评测失败后继续调参，应把原评测集视为已使用数据，并保留新的未见任务。
4. 对单轮生成与执行反馈重试做公平对照：同一任务、模型与提示基础、预算定义和成功标准；报告多轮方案额外花费的调用、token 和时间。
5. 记录真实失败案例和修复前后的变化。小型人工构造任务集只能说明这些任务上的结果，不能外推为 SWE-bench、真实企业仓库或通用修复率。
6. 能独立回答：为什么这样设计状态机；怎样防止修改后复用旧测试结果；取消如何传播；上下文如何选择与截断；工具失败如何处理；如何识别评测泄漏；为什么没有必要为了展示而增加多个 Agent。

简历数字必须来自保留的实际运行记录。尚未完成的 Docker 执行、真实模型评测、跨仓库泛化或并发部署，应写为待验证项，不应写成已经完成的成果。
