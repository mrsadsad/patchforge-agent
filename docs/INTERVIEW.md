# 把作品变成你能讲清楚的项目

## 五分钟演示

1. 打开 8771 工作台，选开源缓存任务，先看来源、原始源码与基线失败。
2. 选择真实模型与多轮修复，观察修改、测试和补丁，而不是只展示自然语言回答。
3. 查看 visible 与 withheld 两层结果，解释后者不返回修复循环的原因。
4. 下载 diff，手动审阅修改是否泛化；指出测试通过并不等于程序永远正确。
5. 打开评测页，对比 direct/repair 成功率、token 和耗时，保留没有提升的结论。

## 必须亲自完成的练习

- 在没有助手代写的情况下，解释并修改一个 runtime 工具。
- 给自己的小型 Python 仓库导入真实缺陷与回归测试，保留导入前代码和参考修复依据。
- 设计一个“测试通过后再次修改”的场景，验证旧测试结果不能用于提交。
- 找到一次模型失败，区分参数错误、代码错误、测试不足、容器错误和调用预算耗尽。
- 为一个失败提出假设并实施修正，在冻结任务上进行对照，不靠改标签或挑重试制造提升。
- 练习 Python、数据结构、网络、数据库与并发基础；项目不能替代面试编码能力。

## 简历描述应与个人贡献一致

可使用的事实骨架：

> 在 AI 协助下构建代码修复 Agent 原型，实现工具调用、受限代码编辑、Docker 测试反馈及补丁交付；设计一次生成与多轮修复对照，记录全部失败、token 和延迟。个人进一步负责（真实完成的部分），在（实际任务来源与数量）上验证（真实结论）。

不要把八项合成样例或两项公开历史回放写成线上仓库、独立测试集、SWE-bench 或生产效率提升。不要写未实现的多 Agent、MCP、语义 RAG 或模型训练。当前数字见 EXPERIMENT_V02.md，首版保留在 EXPERIMENT.md；投递时核对模型、源码与个人贡献。

## 下一阶段的明确验收

这版完成了可运行的工程闭环。更有说服力的投递证据还需要：一批来源可追溯的真实仓库缺陷、与开发过程隔离的评测数据、至少一次亲自完成的失败分析与改进，以及三到五分钟独立讲解。这些是项目建设建议，不是字节官方录用条件。
