# 0.2：从演示闭环到可审阅的仓库修复实验

本轮围绕源码规模、修改可靠性和实验可信度优化。首版实验不覆盖、不替换，当前源码与本轮评测快照分开保存。

| 首版限制 | 0.2 的实现 | 仍需注意 |
| --- | --- | --- |
| 全量源码塞进上下文 | AST 符号索引、问题与失败输出词项排序、初始源码上下文上限 24,000 JSON 字符、按行读取 | 词项检索，不是 embedding RAG；初始上下文还会追加有界基线输出 |
| 工具历史持续增长 | 在 60,000 字符预算下压缩完整旧工具回合，保留初始与最近三组 | 只摘要操作与白名单结果；保护区仍过大时停止 |
| 批量修改后半段失败会留下前半段 | 先暂存并验证全部修改与 Python 编译语法，再写入；普通 IO 失败回滚 | 不宣称断电时多个文件系统写入原子性 |
| 无法尝试和回退 | 最多十个命名检查点，恢复可编辑源码后测试失效 | 不是整个程序状态，也不会撤销外部副作用 |
| 测试缺代码版本标识 | 测试前后计算工作区摘要，两套最终测试必须对应相同版本 | 测试与源码同进程，仍不能抵御恶意代码伪造结果 |
| diff 缺审阅上下文 | 可重复 ZIP，含前后源码、结果、任务公开信息和逐文件 SHA-256 清单 | 不含凭据、任意宿主文件或隐藏测试源码；结果可能包含隐藏测试输出 |
| 只有小型合成任务 | 两项带父提交、修复提交、MIT 许可和原文件摘要的 cachetools 历史缺陷 | 公开回放、非盲测、存在训练数据污染可能 |
| 只有单次尝试统计 | 重复次数、独立任务数、分来源成绩、配对方向与失败分类，逐次存档 | 小样本不报告普遍有效或线上收益 |
| CLI 与服务可能误用同目录 | OS 文件锁拒绝第二个调度器，运行时固定 Docker 镜像 ID | 不支持跨进程调度与多租户部署 |

工具错误严格反馈给模型，不猜测损坏 JSON 的本意；修复策略可在原预算内纠正，一次生成对照仍只有一次请求。没有隐藏重试或把失败换成成功。

开发探测 run `a3b4039eab4e4394` 在增长值任务中通过可见测试，却在“被更新的键先被驱逐”的场景未继续预留完整空间，保留测试检出了容量错误。该次失败及高调用成本保留在开发探测记录，不加入正式重复对照，也不修改保留断言。此后提示增加通用最小修改原则和请求预算提醒，没有向模型传入隐藏断言或参考补丁。

面试可深入解释：批量编辑如何回滚以及崩溃边界；为何工具消息必须整组压缩；如何绑定测试版本；为何重复次数不等于独立样本数；镜像 ID 固定了什么；为何公开历史任务仍不足以证明泛化。

工程源码、关键参数、工具观测与测试输出可审阅；模型会话在内存中，私有 reasoning 字段不展示、不作为审计证据。没有新增未经实现的多 Agent 或训练能力标签。
